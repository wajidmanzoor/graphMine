One boundary, many algorithms

Keep the research logic. Simplify everything around it.

Backend adapters handle dense IDs, CSR conversion, artifact input layouts, GPU resources, and external-ID restoration. Applications see the same high-level lifecycle for every problem.

01

Canonical input

Supply vertices and edges once with stable integer or string IDs. Labels, weights, timestamps, and attributes stay available.

02

Runtime dispatch

Choose the problem and backend at runtime. Unsupported selections return a precise status instead of silently changing algorithms.

03

Typed results

Receive required outputs, requested optional fields, provenance, timings, normalization warnings, and restored external IDs.

Quickstart

Compile once. Query repeatedly.

The default build links every enabled component into one runner. Later requests only parse inputs, initialize the selected runtime, and execute—there is no C++ or CUDA compilation in the query path.

Runtime truth: use graphmine list to see which validated backends are compiled into your binary.

1 Configure and build 
cmake -S library -B library/build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGRAPHMINE_BUILD_CLI=ON
cmake --build library/build --parallel \
  --target graphmine_cli
2 Inspect this build 
library/build/graphmine list --pretty
3 Run an operation 
library/build/graphmine run triangle-counting \
  --graph graph.json \
  --backend tot \
  --list-instances \
  --pretty

Canonical graph input

One JSON graph format at every boundary.

All vertices—including isolated vertices—are declared explicitly. Edges reference stable external IDs. Backend adapters normalize only what the selected problem contract permits.

  • Integer or nonempty string vertex and edge IDs
  • Directedness, self-loop, and parallel-edge policy declared
  • Optional labels, types, weights, timestamps, and attributes
  • Strict validation before backend execution

Predictable results

Outputs explain both the answer and how it was produced.

Always present

Required problem output

Counts, cliques, assignments, scores, or decompositions defined by the selected operation contract.

Flag controlled

Optional materialization

Instances, rankings, per-vertex counts, edge cuts, and other large fields appear only when explicitly requested.

Every execution

Provenance and diagnostics

Backend identity, pinned source commit, execution path, timings, warnings, and structured failures travel with the result.

Native C++ API

The same lifecycle across every problem.

Construct options, choose a backend, instantiate the algorithm, call supports() when capability discovery is useful, then call run() for a typed ExecutionResult<T>.

01Configure typed options
02Create the problem object
03Run and inspect status
maximal_cliques.cpp 
#include <graphmine/graph.hpp>
#include <graphmine/problems/maximal_cliques.hpp>

auto graph = graphmine::Graph::from_edges(
    "sample", {0, 1, 2, 3},
    {{0, 1}, {0, 2}, {1, 2}, {2, 3}});

graphmine::MaximalCliqueOptions options;
options.backend = graphmine::MaximalCliqueBackend::rdmce;
options.minimum_clique_size = 2;
options.optional_outputs =
    graphmine::MaximalCliqueOptionalOutput::total_count;

graphmine::MaximalCliques algorithm(options);
auto result = algorithm.run(graph);
if (!result.ok()) {
  // result.status().code() and .message()
}
